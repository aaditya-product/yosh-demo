# 02 · Information architecture

## The request spine

Everything the client asked for collapses into **one object with a type facet**.
This is the core architectural idea and it must be visible in the UI.

```
Request
  id            REQ-####
  ref           short display ref, e.g. #0BE
  type          service | maintenance | asset | access | concierge | gathering
  property      Villa 12 | The Residence | ...
  requester     resident id, or 'system' for auto-generated
  origin        voice | chat | catalogue | inspection | command
  title         short human line
  items         [{ label, qty }]
  status        new | open | assigned | in_progress | done | cancelled
  priority      normal | high | escalated
  assignee      staff id | null
  eta           ISO timestamp | null
  slaMinutes    number
  createdAt     ISO timestamp
  timeline      [{ at, actor, event }]
  external      { system: 'D365' | 'CAFM', ref: string } | null
```

Consequences to respect while building:

- One board (`L-01`) shows every type. Filters, never separate screens.
- One detail screen (`L-02`) with a type-specific panel slot.
- SLA, escalation, timeline and analytics are written once and apply to all types.
- **Registries are not requests.** Inventory, fleet, wardrobe and art are the
  nouns requests act on. Separate section, separate entity.

## Voice model

Voice does two different jobs. Do not merge them into one component's behaviour.

**Genie — intent capture.** The resident speaks loosely. The system's job is to
understand and structure. Input may contain multiple intents.

**Luna — command execution.** Staff know the system. Speech replaces four taps.
Precision matters more than interpretation. Always undoable.

Both resolve through the same visual pattern:

```
idle → listening (live transcript) → parsing → confirm card → committed
```

The **confirm card is the most important component in the build.** Voice into a
chat bubble looks like a toy; voice into a structured card the user confirms
looks like a product. Low-confidence fields render as visibly editable chips.

## Genie — resident rail

Existing Genie rail pattern kept exactly: vertical, persistent, pill
container, icon above label, teal icons, three states (collapsed sliver /
icon column / expanded with labels), floating over content.

**Confirmed tile set** (source: `09-genie-reference.md` addendum, Abu Dhabi
Figma, verified directly against the person's own screens):

| Item | Opens | In demo |
|---|---|---|
| My Requests | Requests overlay (filterable list) | yes |
| Housekeeping | Housekeeping catalogue + cart | yes |
| Maintenance | Same catalogue + cart component, different categories | yes |
| Event Planning | Event request form → chat thread | yes |
| Chauffeur | Transport booking, 3-step panel | yes |
| Profile | Profile overlay | yes |

No Spa, Activities, Restaurant, Dining or Store — confirmed out of scope,
these belong to the source app's resort configuration, not Yosh's.

**Chat is not a rail item.** It's reached two ways: tapping `Chat with X` on
the home status banner, or tapping `Need Help?` on a request card. This is
also where custom/ad-hoc requests and follow-ups happen — there is no separate
composer screen.

**Catalogue is not a rail item either.** Inventory/warehouse/art browsing is
reached contextually from Event Planning (selecting items for a gathering) or
from a request's detail, using the same category-rail-plus-grid pattern
documented for Luna's Registry.

Voice affordance sits inside the Chat input field as a trailing mic icon —
tap to transcribe live, auto-sends on the person finishing speaking. It is
**not** a persistent rail-level control; it lives inside the one input field
in Chat.

## Luna — operations nav

Extends the existing grouped-chip panel. Two groups added, existing ones kept.

```
Operations     Requests · My Requests · Archive
Assets         Registry · Inventory · Fleet
Compliance     Inspections · Action Plans
Clients        Client Center · Chat · Chat History · Feedback
Admin          Admin · Profile · Announcements
```

Plus **Insights**, reached from the LUNA STATS tab at the top of the page, which
already exists in the live build.

Notes carried from the live build — respect these, they are already shipped:

- **Schedule is a segmented toggle** beside Requests (`Request | Schedule`), not
  a nav chip
- **Property switcher is a horizontal chip row** across the top, above the page
  title. Multi-property is already solved.
- The command bar `What do you need?` sits at the foot of the nav panel
- The orb is a live call-handling widget with Transfer — distinct from the
  command bar. Do not merge them.

Navigable in the demo: Requests, Registry, Inspections, Action Plans, Insights.
Everything else renders in the panel and does nothing.

## Command bar behaviour

Three classes of input, one field:

| Class | Example | Result |
|---|---|---|
| Navigate | "overdue requests at Villa 12" | Opens `L-01` pre-filtered |
| Create | "gate pass for the AC contractor tomorrow 9am" | Pre-filled confirm card |
| Act | "assign the AC job to Rahul, ETA 40" | Executes, with undo |

All three appear in the script. This is how the long-tail RFI modules are
reachable without fourteen nav destinations.
